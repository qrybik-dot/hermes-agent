# Task Intake Router

## 1. Введение и назначение
Task Intake Router предназначен для структурированного анализа входящих задач. Он помогает определить размер, сложность, риски и необходимые инструменты перед началом работы. Это предотвращает хаотичное выполнение, снижает затраты контекста и защищает систему от деструктивных изменений.

---

## 2. Матрица классификации задач (`task_size`)

Задачи классифицируются по четырем уровням размера:

| Размер (`task_size`) | Критерии | Допустимый режим (`execution_mode`) | Политика запроса подтверждения (`ask_policy`) |
| :--- | :--- | :--- | :--- |
| **Simple** (Простая) | Вопрос-ответ, поиск информации, просмотр статуса, чтение 1-2 файлов, правки Markdown/docs без runtime-эффекта. | Direct (Прямое выполнение) | `do_not_ask` (полная автономия) |
| **Normal** (Обычная) | Написание скрипта, интеграция API, создание новой фичи без изменения ядра, редактирование 3-5 файлов. | Step-by-Step (Пошаговый) | `ask_once` или `ask_before_write` |
| **Large** (Большая) | Изменение ядра Hermes, сложные рефакторинги, перенос данных, слабая формулировка («сделай хорошо»). | Plan-First (Сначала план) | `ask_before_write` (требуется согласование плана/контракта целей) |
| **Risky** (Рискованная) | Работа с `systemd`, `sudo`, `root`, изменение `.env`, системные конфиги, права доступа, удаление данных. | Safe-Write & Rollback | `ask_before_risky_step` (обязательно на каждый шаг записи / перезапуска) |

---

## 3. Политика подтверждения (`ask_policy`)
Определяет поведение агента перед выполнением действий:
- **`do_not_ask`**: выполнение выполняется автономно, без подтверждения пользователя (допустимо для простых read-only команд и не-runtime правок документов).
- **`ask_once`**: достаточно один раз спросить подтверждение перед запуском всей цепочки действий.
- **`ask_before_write`**: обязательное подтверждение непосредственно перед записью/модификацией файлов проекта.
- **`ask_before_risky_step`**: подтверждение требуется для каждой отдельной рискованной команды (sudo, systemd restart, удаление, запись в .env).

*Важное правило для Simple + write_scope=project:*
Если задача классифицируется как Simple, но масштаб записи `write_scope=project` (изменение кода), то автономия без подтверждения (`do_not_ask`) допускается **только для очевидных docs/markdown-правок без runtime-эффекта**. Если правка затрагивает код Python/JS/TS, политика повышается до `ask_before_write`!

## 4. Оценка домена и рисков (`task_domain`, `ambiguity`, `risk`)

Каждая входящая задача должна пройти экспресс-оценку по следующим критериям:

1. **Домен задачи (`task_domain`):**
   - *system*: Настройка ОС, системные пакеты, службы, порты.
   - *code*: Написание или модификация Python/JS/TS кода.
   - *content*: Тексты, Markdown, документация, навыки (skills).
   - *graphic*: Генерация картинок, схем, инфографики.
   - *research*: Поиск информации в сети или в истории сессий.

2. **Степень неопределенности (`ambiguity`):**
   - *low*: Четкая инструкция, конкретные файлы и ожидаемый результат.
   - *medium*: Понятная цель, но пути решения требуют выбора.
   - *high*: Размытая цель («улучши логику», «сделай красивее», «что-то тормозит»).

3. **Степень риска (`risk`):**
   - *low*: Чтение, локальное тестирование, создание новых неиспользуемых файлов.
   - *medium*: Замена файлов проекта, добавление зависимостей в pyproject.toml / requirements.txt / package.json / package-lock, установка любых пакетов (pip/npm install). **Любые dependency changes автоматически классифицируются как risk: medium минимум!**
   - *high*: Модификация системных конфигов, остановка gateway, удаление файлов, редактирование файлов авторизации, изменение `.env`.

4. **Масштаб записи (`write_scope`):**
   - *none*: Только чтение (Read-only).
   - *local*: Запись только в `.tasks/` или `docs/`.
   - *project*: Изменение исходного кода проекта.
   - *vps*: Изменение системных путей или глобального окружения.

## 5. Инструменты и зависимости (поля разделены)

- **needs_web** (boolean): Требуется ли поиск в Google/Bing для уточнения актуальной информации.
- **needs_context7** (boolean): Требуется ли поиск по внешним API/библиотекам через resolve-library-id / query-docs.

## 6. Goal Contract Builder (Спецификация целей)

Для задач класса **Large** (Большая) или с высокой неопределенностью (**ambiguity: high**) агент обязан составить черновик **Goal Contract** (Контракт целей) с предположениями (assumptions) и показать его пользователю перед выполнением, **избегая длинных опросников**:

### Шаблон Goal Contract
```markdown
### КОНТРАКТ ЦЕЛЕЙ (GOAL CONTRACT)
- **Исходная задача**: [Краткое описание исходного запроса]
- **Предположения (Assumptions)**:
  - [Что мы предполагаем о текущем окружении/коде, чтобы не переспрашивать]
- **Ожидаемый результат (Definition of Done)**:
  1. [Конкретный измеримый критерий 1]
  2. [Конкретный измеримый критерий 2]
- **Ограничения (Constraints)**:
  - [Что делать нельзя / какие ресурсы не трогаем]
- **Критерии верификации (Verification)**:
  - [Как доказать работоспособность, например: вывод команды X]
- **Условия остановки (Stop Conditions)**:
  - [Когда остановиться и спросить: например, лимит времени, отсутствие API-ключей]
```

## 7. Протокол выполнения (Execution Mode)

1. **Direct (Прямой)**: выполнение за 1-2 быстрых вызова инструментов без промежуточных планов.
2. **Step-by-Step (Пошаговый)**: разделение на логические шаги с отметкой прогресса.
3. **Plan-First (Сначала план)**:
   - Шаг 1: Анализ файлов.
   - Шаг 2: Создание плана в `.tasks/` или в чате.
   - Шаг 3: Согласование плана.
   - Шаг 4: Пошаговая реализация.
   - Шаг 5: Верификация тестами.
4. **Safe-Write & Rollback (Безопасный)** (обязателен для `risky/system/vps` задач):
   - **Правило**: Сначала проводится только read-only аудит окружения и файлов.
   - Запись, модификация или перезапуск служб выполняются **только после отдельного подтверждения** каждого шага.
   - Обязательное создание резервной копии изменяемого файла (`cp file.ext file.ext.bak`).
   - Использование `patch` вместо полной перезаписи.
   - Наличие готового bash-скрипта или команды для отката изменений.
