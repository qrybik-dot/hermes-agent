# Hermes Backlog

## HIGH · Пересмотреть fallback при исчерпании лимита OpenAI Codex

**Статус:** BACKLOG
**Добавлено:** 2026-06-28

### Проблема

Для ролей `planning`, `coding`, `long_context` и `server_debug` gateway сейчас отключает fallback, если выбран `openai-codex`. Это защищает качество, но при подтверждённом `usage_limit_reached` приводит к повторным заведомо бесполезным запросам и `INCOMPLETE`, хотя доступный бесплатный провайдер по текущей подписке может продолжить задачу.

### Предлагаемое решение

- Сохранить quality lock для временных 429, capacity и сетевых сбоев.
- Разрешить одноразовый fallback только для подтверждённого `usage_limit_reached` с известным временем сброса.
- Переходить на заранее настроенную модель соответствующей роли через существующую подписку/CLIProxy, без платного API.
- Сохранять исходные toolsets, task state, approvals и continuation contract.
- В отчёте явно указывать `Codex -> fallback`, причину и фактическую модель.
- Не повторять исчерпанный Codex в рамках той же задачи до наступления `resets_at`.

### Acceptance

1. Codex `usage_limit_reached` не делает три одинаковых запроса.
2. Крупная задача продолжает работу на разрешённой fallback-модели.
3. Обычный transient 429 не вызывает неконтролируемую смену качественной модели.
4. Пользователь видит факт fallback и может продолжить исходную task ID.
5. Есть тесты для quota, transient 429, отсутствующего fallback и continuation.

### Риск

Автоматическая смена модели может снизить качество или изменить поведение инструментов. Реализовывать отдельно после выбора конкретной fallback-модели для `coding/server_debug` и smoke-теста на реальной задаче.
